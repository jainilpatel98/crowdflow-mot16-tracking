MOT PROJECT ACTION PLAN

Date: 2026-03-23

Main objective:
Complete a clear, course-ready MOT16 pedestrian tracking project with one understandable baseline, one visual demo path, and one concise final write-up.


PHASE 1. Lock the project scope

What to do:

- Treat Faster R-CNN + simple IoU tracker as the primary project.
- Treat YOLO + BoT-SORT as a secondary comparison/demo, not the main reported method unless the assignment explicitly allows it.
- Use MOT16/train for training and internal validation.
- Use MOT16/test only for demo-style inference unless an official submission is planned.

Outputs for this phase:

- one sentence project statement
- one list of primary deliverables
- one list of optional stretch goals

Done when:

- there is no confusion about which method is the official baseline
- there is no plan to tune on MOT16/test


PHASE 2. Validate the dataset and folder assumptions

What to do:

- confirm all 7 train sequences are readable
- confirm all validation sequences have GT available
- confirm image counts match sequence metadata
- confirm the GT filtering rule is consistent:
  mark == 1 and class == 1 for pedestrian detection training
- confirm output directories are organized and named consistently

Outputs for this phase:

- a short dataset sanity summary
- a table listing train and validation sequences
- one note describing any skipped or problematic sequences

Done when:

- the team can trust the data pipeline before training or evaluation


PHASE 3. Finish the detector baseline first

What to do:

- run the Faster R-CNN notebook end-to-end through training
- save the best checkpoint and training history
- record detector threshold choices used for inference
- avoid over-tuning augmentations unless the baseline is already stable

What to monitor:

- training loss trend
- validation loss trend
- obvious overfitting
- whether predicted boxes on validation frames look reasonable

Outputs for this phase:

- best model checkpoint
- training history json or csv
- 3 to 5 example validation frames with predicted boxes

Done when:

- the model produces reasonable pedestrian detections on held-out sequences


PHASE 4. Finish the tracker path

What to do:

- run the detector on one validation sequence first
- feed detections into the IoU-based tracker
- save one MOTChallenge-format result file
- verify the file has the expected 10-column format
- only after one sequence works, scale to the second validation sequence

What to monitor:

- whether IDs remain stable for a moving pedestrian
- whether missed detections break tracks immediately
- whether crowded scenes create many ID switches

Outputs for this phase:

- one txt result file per evaluated sequence
- one annotated video or GIF per evaluated sequence

Done when:

- the project can generate tracking outputs reproducibly for at least the validation set


PHASE 5. De-risk evaluation early

What to do:

- verify MATLAB Engine and MOT devkit availability before final report week
- run MOTMetrics on one known-good result file first
- record the main metrics that matter:
  MOTA
  MOTP
  IDF1
  precision
  recall
  false positives
  false negatives
  ID switches

Important interpretation rule:

- detector validation loss is not the final project score
- the final report should emphasize tracking metrics plus visual behavior

Outputs for this phase:

- one metrics summary table for each validation sequence
- one combined average or summary table

Done when:

- the team can show both qualitative and quantitative results


PHASE 6. Add the YOLO comparison only after the baseline works

What to do:

- run the YOLO notebook on one or two MOT16 sequences
- keep the existing BoT-SORT config as a comparison setup
- generate visually strong GIFs or videos
- compare identity continuity and visual smoothness against the Faster R-CNN baseline

Important boundary:

- do not let the YOLO demo replace the main baseline unless that is a deliberate report decision
- keep the write-up honest that the methods differ in detector and tracker strength

Outputs for this phase:

- 1 to 2 YOLO tracking demos
- one short comparison paragraph

Done when:

- the project can explain both the baseline and the stronger demo path clearly


PHASE 7. Write the report and class presentation around the actual findings

Recommended report structure:

- Project goal
- Dataset and benchmark
- Baseline method
- Training setup
- Tracking method
- Evaluation setup
- Results table
- Qualitative examples
- Failure analysis
- Comparison with YOLO demo
- Conclusion and next steps

Recommended presentation structure:

- 1 slide: problem and motivation
- 1 slide: MOT16 dataset and benchmark rules
- 1 slide: Faster R-CNN detector pipeline
- 1 slide: IoU tracker design
- 1 slide: metrics and results
- 1 slide: qualitative examples
- 1 slide: YOLO + BoT-SORT comparison
- 1 slide: lessons learned and future improvements

Done when:

- the story is easy to explain from dataset to method to result


PRIORITY ORDER

Highest priority:

1. Confirm evaluation path works
2. Complete Faster R-CNN baseline on validation sequences
3. Produce at least one clean metrics table and one clean qualitative example

Medium priority:

4. Improve detector thresholds and tracker settings
5. Run the second validation sequence
6. Package outputs neatly for the report

Lower priority / stretch:

7. Broader YOLO comparison
8. Additional tracker experiments
9. More polished visualizations


WHAT NOT TO DO

- Do not spend most of the time on cosmetic notebook cleanup before the evaluation path works.
- Do not tune on MOT16/test.
- Do not rely only on detector loss curves as proof that tracking works.
- Do not leave MATLAB/devkit verification until the very end.
- Do not mix Faster R-CNN baseline results and YOLO demo results without labeling them clearly.


MINIMUM CHECKLIST BEFORE CALLING THE PROJECT DONE

- dataset split is documented
- detector checkpoint is saved
- tracking txt files are generated
- MOT metrics are computed on held-out train sequences
- at least one annotated visual output exists
- final report text explains both strengths and failure cases
